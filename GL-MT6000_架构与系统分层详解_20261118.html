01硬件架构

MT7986A 是联发科的 Filogic 830 平台，四核 Cortex-A53。这颗 SoC 的关键点在于它自带硬件 NAT 加速（HNAT）和双频 Wi-Fi 6 射频，所以 CPU 本身很闲（实测 load average 0.11），压力都在转发平面。

为什么"千兆 WAN"这点值得注意

MT6000 的 WAN 口物理能力是 2.5Gbps，但实测 /sys/class/net/eth1/speed 是 1000——说明上级设备（光猫/交换机）只给到千兆。你当前宽带是移动 CGNAT，实际出口远低于千兆，所以这不是瓶颈。但如果将来换千兆以上宽带，要记得检查这一环。

1.2 有线和无线是怎么接的（DSA 架构，不是 swconfig）

这台机器用的是内核 DSA（Distributed Switch Architecture），不是老的 swconfig。区别很实际：

  • lan1 ~ lan5 是独立的内核网络接口，可以直接 ip link / tc / tcpdump 操作，也能单独设 IP。
  • 它们都是 eth0 的 DSA 从属口（iflink 指向 eth0）。用 ip -d link 能看到 portname p0…p5、switchid 00000000。
  • /etc/config/network 里没有 config switch 段——写了也不生效。VLAN 要用 config bridge-vlan（DSA 风格），或直接操作 bridge vlan。

02存储与分区：本机最关键的结构差异

这一节是全文最重要的部分——它决定了你所有"改系统"的操作方式

绝大多数 OpenWrt 教程默认你的 overlay 是 ubifs 挂在 ubi0_2 上。这台机器不是。它是 f2fs 文件系统镜像，用 loop 设备挂载，镜像文件存在 eMMC 的第 7 个分区里。

2.1 为什么这个设计很聪明（也为什么它让你玩法更多）

  • 刷不坏：固件本体在 squashfs 里只读，你的所有改动都在 f2fs 镜像里。恢复出厂 = 清空镜像，固件本体毫发无伤。
  • 空间不是问题：7.2 GB overlay，已用 592 MB，还剩 6.6 GB。这意味着你可以装 Docker、可以装 OpenClash 全套规则库、可以本地跑一个轻量服务。这跟 MT3000 那种 142MB 小 flash（要精打细算）是两个世界。
  • f2fs 比 ubifs 更适合大容量 eMMC：有 GC、discard、后台整理（进程里能看到 f2fs_flush-7:0、f2fs_gc-7:0）。
  • 但它不支持 ubi 的"原子写入/坏块全盘重映射"：eMMC 有自己的磨损均衡，所以够用，但掉电保护不如 ubifs。别在它上面放高度依赖掉电安全的数据。

03系统分层模型

理解这台路由器的关键，是把"一个盒子"拆成六个纵向层。每一层有自己的配置文件、自己的 Web 界面、自己的改法和自己的坑。很多人改坏路由器，是因为在错误的层动手——比如想改 Wi-Fi 却去改 iptables。

3.1 各层"能改什么 / 改了怎么生效"

层改哪里典型操作怎么让它生效
L0u-boot-env、factory 校准改 MAC、改启动参数高危 需要 fw_setenv，改错直接不进系统。factory 区改坏 = Wi-Fi 永久失校
L1/etc/sysctl.conf、/proc/sys/、装 kmod-*开 conntrack 调优、开 BBR、加 tcp 拥塞控制sysctl -p 或写 /etc/sysctl.d/ 后重启服务；模块用 insmod/modprobe

L3/etc/init.d/、/etc/rc.d/、/etc/rc.local开机自启脚本、加自己的守护进程/etc/init.d/X enable 建软链；rc.local 只在开机最后执行一次

"配置写进去了" ≠ "生效了" —— 这台机器上这条教训尤其贵

GL 固件的 uci apply 只负责提交配置文件，不会重建防火墙、不会重挂 fstab、不会重启 repeater 服务。所以每一次改完，都要落到实测层验证：防火墙看 iptables -t mangle -L 的 pkts 是否在涨、挂载看 /proc/mounts 的 rw 标志、无线看 iwinfo 的 ssid 非空。

3.2 UCI 是这台机器真正的"配置总线"

/etc/config/ 下有 80 个配置文件。它们全都是同一种语法（UCI 的 section/option 结构），所以一套 uci 命令可以操作全部配置——包括第三方插件（OpenClash、AdGuardHome）。这是你扩展玩法时最省力的入口。

# 看有哪些配置
uci show | cut -d. -f1 | sort -u

# 看某个配置的全部内容（结构化）
uci show openclash

# 看某一段
uci show network.wan

# 备份某一项（改前必做）
cp /etc/config/firewall /etc/config/firewall.bak-$(date +%Y%m%d)

# 改（注意：set 后必须 commit）
uci set network.wan.peerdns='0'
uci commit network
/etc/init.d/network reload

# 查"改了但没提交"的东西 —— 排查"为什么没生效"第一步
uci changes

  • 改 iptables / nftables 规则 → 放 /etc/firewall.user（每次防火墙重建都执行，不只在开机时）。放 rc.local 只在开机跑一次，防火墙 reload 后规则就没了。

07网络数据面：包是怎么出去的

这是整台机器性能最关键的一层，也是最容易被"改规则改坏"的一层。理解它你才知道为什么这台机器 CPU 长期 0%、为什么装某些插件会让网速腰斩。

7.1 实测的 iptables 规则链（只读抓取）

    0      0 TCPMSS  tcp -- eth1 *     /* Zone wan MTU fixing */ clamp to PMTU
 1166  893K NFQUEUE  all -- *  *      connbytes 0:32 direction both NFQUEUE num 0 bypass
三条规则各是什么，值得记住
  • FULLCONENAT：全锥形 NAT（Full Cone）。这是游戏联机 / P2P / 某些语音通话能正常工作的关键。它替代了普通 MASQUERADE，对 NAT 类型要求严格的游戏是好事。
  • TCPMSS clamp to PMTU：MTU 修正。因为 WAN 侧是 PPPoE/隧道时 MTU 小于 1500，不做这个很多网站会"能 ping 通但打不开"。mtu_fix=1 开着。
  • NFQUEUE connbytes 0:32：把每个连接的前 32 个包送进用户态（给 DPI / OpenClash 判断），之后自动 bypass 走快路径。这就是"DPI 开着但不拖网速"的设计。

7.2 HNAT 硬件加速：可观测的入口

/sys/kernel/debug/hnat/ 是 MTK 暴露的 HNAT 状态目录，这是排查"为什么某类流量慢"的利器，原版 OpenWrt 没有这个。

文件能看什么
hnat_version硬件加速模块版本
hnat_setting当前加速开关、支持哪些协议（IPv4/IPv6/TCP/UDP/PPPoE…）
all_entry / hnat_entry已卸载到硬件的连接表 —— 能看到哪些流真正走了快路径
cpu_reason包为什么没走硬件（被打回 CPU 的原因统计）——排查慢速最有用
external_interface哪些接口启用了外部加速
hook_toggle / mape_toggle挂钩点与 MAP-E 开关
mcast_table组播转发表（IPTV 多播相关）
# 看当前 HNAT 是否开着、支持什么
cat /sys/kernel/debug/hnat/hnat_setting

# 看有哪些连接被硬件加速了（数量多说明加速在工作）
cat /sys/kernel/debug/hnat/all_entry | head -20

# ★ 排查"某个应用很慢"：看它为什么没被加速
cat /sys/kernel/debug/hnat/cpu_reason
什么会让 HNAT 失效（网速掉一半以上）
  • SQM / QoS / cake-autorate：整形必须逐包调度，必然绕过硬件加速。本机这些服务都没启用（sqm/eqos/cake-autorate 在 rc.d 有入口但配置未开），所以速度不受影响。开了就是"用带宽换低延迟"的取舍。
  • 复杂的 iptables 匹配（大量 -m 规则、连接标记、TPROXY 分流）。
  • 流量统计类工具（nlbwmon、vnstat）在极高流量下可能干扰。
  • OpenClash 的 TUN 模式比 fake-ip 混合模式对加速更不友好。
